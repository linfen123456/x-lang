# X-Lang 2026 设计规格（草案）

> 状态：草案，等待项目所有者确认
> 责任角色：语言设计、编译器、运行时、标准库、工具链
> 最后更新：2026-08-17
> 上游依据：`XLF-*`、`XLC-*`、`XLE-*`、现有八份顶层母版
> 下游输出：核心 RFC、ADR、可执行规范、MVP Workspace 与符合性套件

## 0. 前提假设

- 1.0 首要场景是系统工具、CLI、本地服务和高性能网络服务；
- 安全与正确性高于语法便利和功能数量；
- 初始编译器继续使用 Rust + LLVM，但实现选择不得成为语言语义；
- Web、GUI、ML/GPU 和 AI Runtime 属于后续官方生态或研究；
- 本规格中标为“候选”的能力只有经过 RFC 才能成为稳定承诺；
- 项目资源尚未确定，因此路线按证据门禁排序，不预设发布日期。

这些是假设而不是既成事实。第 15 节由项目所有者确认后，本规格才能从“草案”进入“评审中”。

## 1. 目的

本规格把“打造 2026 年最有竞争力的 X-Lang”转换为可验证的产品和工程目标。项目不宣称在所有场景绝对最优，而是在明确目标场景中追求安全、性能、简洁、可诊断和工程效率的 Pareto 最优解。

首要用户是：

- 编写系统工具、CLI 和本地服务的开发者；
- 构建高性能网络服务和基础设施的团队；
- 需要原生性能、资源确定性和跨平台发布的工程团队；
- 希望 AI 辅助开发可验证、可追溯，而不是自动绕过质量门禁的团队。

首要成功场景是：

1. 新用户能在一天内完成安装、学习、调试和发布一个非平凡 CLI；
2. 资深开发者能构建内存安全、数据竞争安全且性能可预测的原生服务；
3. 编译器对错误输入不崩溃，并提供稳定、可操作、机器可读的诊断；
4. 同一项目在已声明的 Tier 1 平台上可复现构建，在其他平台上按能力矩阵获得一致的规范行为；
5. 每项稳定能力都能追溯到规则、实现、测试、基准和发布证据。

## 2. “最优”的可验证定义

X-Lang 不使用无边界的“最好”“最快”“最简单”。所有比较必须明确工作负载、平台、版本、权重和失败条件。

设计决策按以下优先级裁决：

1. 正确性、内存安全和数据竞争安全；
2. 规则一致性、可诊断性和可维护性；
3. 常见原生工作负载的运行时性能与资源可预测性；
4. 编译反馈速度和开发者效率；
5. 跨平台与互操作；
6. 语法便利和功能数量。

任何低优先级目标不得通过静默削弱高优先级目标实现。性能模式可以显式放宽浮点确定性，但不能默认关闭内存安全；语法糖可以缩短代码，但不能产生不可解释的隐式 I/O、锁、网络访问或所有权转移。

### 2.1 竞争力记分卡

| 维度 | 1.0 最低证据 | 不合格条件 |
|---|---|---|
| 正确性 | 每条 CORE 规则映射正例、反例和参考结果；差分测试通过 | 存在未归属的可观察语义 |
| 安全 | 在已批准内存模型覆盖范围内，Safe X 不产生已列明的 UB；unsafe/FFI 有显式义务和审计面 | 正式内存模型未批准却宣称 Safe X 已稳定，或安全代码可制造已列明 UB |
| 简洁 | 语法预算、学习实验、任务对照和诊断理解率达标 | 依靠新增关键字解决库级问题 |
| 运行性能 | 与 C/Rust/Go 同口径基准，公布原始数据和反例 | 只展示单一微基准或最佳样本 |
| 编译体验 | 编辑反馈、冷构建、增量构建有版本化 SLO | 为速度跳过验证或产生过期结果 |
| 生态 | 安装、包解析、IDE、C FFI、发布闭环可复现 | 用规划目录或官方包数量代替用户证据 |

## 3. 范围与非目标

### 3.1 已承诺的 1.0 设计原则

- 静态类型、显式失败、显式 I/O、显式同步和显式 unsafe 边界；
- Safe X 的稳定范围必须由正式内存模型和并发模型覆盖；
- 语言核心不依赖 LLVM、操作系统、云、AI、GUI 或领域框架；
- 不通过隐式 GC、自动插锁或隐藏运行时行为伪造简洁；
- 每项稳定语义都有规范规则、诊断和符合性测试；
- 任何未在 P0 获批的候选能力必须延期或缩减，不能靠模糊规则进入 1.0。

### 3.2 需要 RFC 批准的 1.0 候选集

| 候选能力 | 进入 1.0 的最低前置条件 |
|---|---|
| UTF-8 源码与 Unicode 标识符 | Unicode 17 Profile、安全规则、源码位置和三平台测试获批 |
| 模块、导入和可见性 | 名称解析、循环、包边界和兼容规则获批 |
| 标量、复合类型与 ADT | 布局可见性、模式穷尽和数值语义获批 |
| 局部双向类型推断 | 公开 API 显式边界、失败诊断和复杂度预算获批 |
| 泛型和最小 Trait | 一致性、对象安全、终止预算和单态化规则获批 |
| 所有权、借用、生命周期与 RAII | 正式内存模型、Drop 顺序、unsafe 义务和 soundness 门禁获批 |
| `Option`、`Result`、传播和 panic | 失败分类、清理、abort/unwind 和 FFI 边界获批 |
| 闭包、迭代器和最小结构化并发 | 捕获、状态机、取消和析构语义获批 |
| Safe/unsafe 与稳定 C ABI 子集 | 布局、调用约定、所有权、错误和线程契约获批 |
| `core`、`alloc`、`std` | API、复杂度、平台能力和稳定性政策获批 |
| 最小 const-eval | 只支持常量值、数组长度和枚举判别式；确定性和预算获批 |
| 核心 CLI 闭环 | `check/build/run/test/fmt/doc/doctor` 契约和退出码获批 |

候选集不是已经承诺的最终语法或功能列表。P0 结束时每一项必须是“批准”“缩减”或“延期”，不允许保留阻塞性“待决策”。

### 3.3 明确不进入 1.0 核心

- 类继承、隐式 null、隐式异常传播和隐式数字窄化；
- 编译器自动插锁、隐式网络访问、隐式持久化或生产自动热补丁；
- 完整 Effect System、Specialization、通用反射和超出最小 const-eval 的编译期执行；
- 可选 GC、过程宏、稳定 X 原生动态 ABI 和通用 C++ ABI；
- Web UI、样式 DSL、GUI、移动端、ML/GPU、ZKP、eBPF 和硬实时；
- “一次编写在所有平台像素和行为完全一致”的承诺；
- 以功能数量作为语言先进性的评价方式。

上述能力可以进入独立 RFC、官方生态或 Research，但不得增加 1.0 核心关键字，不得成为编译器前端依赖，也不得阻塞首个稳定版本。

## 4. 语言设计方向与 RFC 约束

本节全部状态为 `候选`，不是已批准语言规则。其中“必须/不得”表示未来 RFC 若选择该能力时不可违反的安全、复杂度和可诊断边界，不表示语法或行为已经稳定。只有链接到已批准 RFC、写入 `specs/` 并具有符合性测试的条目才能转为 `已批准`；草案条目不得生成 Stable 实现或被当作兼容承诺。

### 4.1 语法与可读性预算

- 表达式优先，但控制流不得依赖隐蔽的求值或析构顺序；
- 一种概念只保留一种首选写法，兼容别名和语法同义词不进入 1.0；
- CORE 保留关键字预算暂定不超过 48 个，超出必须经 RFC 删除或替换既有机制；
- 稳定内置属性预算暂定不超过 16 个，其余采用库、工具或命名空间扩展；
- 禁止用户自定义运算符和可改变语法解析规则的宏；
- 所有语法糖必须提供唯一、可打印、可测试的脱糖结果；
- 格式化器必须幂等，`parse → format → parse` 保持语义等价。

关键字和属性预算是复杂度警报线，不是证明简洁的充分条件。最终判断还需真实用户任务实验。

### 4.2 类型系统

- 采用静态、名义类型为主的类型系统；结构类型只用于明确的受限边界；
- 局部表达式使用双向推断，函数签名、公开常量和公开类型边界必须显式；
- 不提供隐式可空类型；缺失值使用 `Option<T>`；
- 数值类型宽度明确，不进行可能丢失信息的隐式转换；
- 泛型默认单态化，动态分派必须通过显式 Trait Object；
- Trait 采用一致性规则，1.0 不引入 Specialization；
- GAT、HRTB 只在核心库存在不可替代用例且求解器预算通过后进入稳定候选；
- 编译器必须限制递归求解深度、时间和内存，并对超限给出可操作诊断。

### 4.3 所有权、内存和资源

- 值默认具有单一所有者；赋值和传参的移动/复制资格由类型规则决定；
- 多个共享借用或一个独占借用，不允许二者重叠；
- 资源通过 RAII 确定释放，析构顺序属于规范性可观察行为；
- 在已批准内存模型覆盖的规则内，Safe X 不得产生悬垂引用、重复释放、越界访问、未初始化读取和数据竞争；
- `unsafe` 只关闭特定静态义务，不关闭边界检查、类型或审计规则的其余部分；
- Pointer Provenance、布局、别名、对象生命周期和原子内存序必须形成正式内存模型；该 RFC 批准前不得标记 Safe X 为稳定；
- 内存模型必须维护 UB 分类表；每个 `unsafe` 操作列出调用者义务、实现者义务和可验证反例；
- 任何 soundness 缺陷按发布阻断级处理，并记录受影响版本、最小复现和修复验证；
- OOM、栈溢出、panic、取消和进程终止分别定义，不用一个异常机制模糊处理。

### 4.4 错误与失败

- 可恢复错误使用 `Result<T, E>`；不存在隐式 checked exception；
- `?` 只执行结构化传播和显式转换，不执行日志、重试或进程退出；
- panic 用于破坏内部不变量或不可继续状态，不作为普通业务分支；
- 默认 panic 策略由构建 Profile 显式选择，但不得跨 C FFI 边界传播；
- 取消、超时、部分写入和资源耗尽是独立错误语义；
- 公共错误具有稳定代码、上下文链和机器可读形式，不依赖字符串匹配。

### 4.5 并发与异步

- 线程安全资格由显式自动 Trait 表达，禁止编译器静默插锁；
- 以结构化并发为首选模型：任务必须属于作用域、Task Group 或显式分离句柄；
- 取消是协作式、可观察的状态转换，规范取消点和清理保证；
- `async/await` 的求值、借用、析构和 panic 行为必须能降级为可打印状态机；
- Runtime 调度策略不是语言语义；语言只规定 Future/Task 的可观察契约；
- Channel、Mutex、RwLock、Atomic 位于库层；内存序遵循正式并发模型；
- 硬实时不作为通用目标，软实时能力必须公布分配、阻塞和调度边界。

### 4.6 宏与编译期执行

- 1.0 只稳定卫生声明宏，并保留完整 Span 来源链；
- 1.0 的最小 const-eval 只处理无 I/O、无分配或受限分配、保证终止预算的常量表达式；
- 过程宏和通用 Comptime 延后到 P5+，通过独立进程或 WASI Component 沙箱探索；
- P5+ Comptime 默认确定、能力受限且有时间、内存和输出预算；
- P5+ 文件、环境、网络、时钟和随机数访问必须显式声明并进入缓存键；
- 任何编译期执行失败不得破坏编译器进程，输出必须可复现、可审计和可最小化。

### 4.7 ABI、版本与互操作

- 1.0 稳定 C ABI 子集，不承诺稳定的 X 原生动态 ABI；
- 公开布局必须显式标注；未标注布局由编译器保留优化自由；
- FFI 必须声明所有权、生命周期、线程资格、错误和释放函数；
- C++、Python、JVM、Node.js 绑定通过独立 SDK 和生成器提供；
- 语言版本与 Edition 分离：Edition 改变源码迁移规则，不静默改变已编译库的 ABI；
- 破坏性变化必须有 API diff、迁移工具、弃用窗口和回滚路径。

## 5. 编译器与运行时架构

### 5.1 模块化单体优先

早期实现采用“模块化单体”，而不是立即创建约两百个独立 crate。只有满足以下至少一项时才拆成独立包：

- 必须独立发布或独立版本化；
- 存在明确的安全、进程或故障隔离边界；
- 已有两个以上稳定消费者；
- 编译并行、缓存或所有权边界具有测量收益；
- 由独立团队长期负责并具有稳定公共契约。

P0/P1 Workspace 原则上控制在 6～10 个可构建成员：

```text
compiler/x-compiler      # Source、Lexer、Parser、Semantic、HIR/MIR 的内部模块
compiler/x-codegen-llvm  # LLVM 适配层
runtime/x-runtime        # 最小 Runtime ABI 与平台适配
library/x-core           # 无操作系统依赖的核心库
library/x-alloc          # 分配类型与可替换 Allocator 契约
library/x-std            # 操作系统与平台能力
tools/x-cli              # check/build/run/test 等命令入口
tests/x-conformance      # 规则级与端到端符合性
tools/x-spec             # 规则、链接和追溯检查
```

模块边界经过实现和依赖数据验证后再抽取，不为规划中的未来消费者预建空 crate。

### 5.2 编译流水线

```text
SourceMap
  → lossless Token/CST
  → typed AST
  → name resolution + type/trait/borrow checking
  → typed HIR
  → control-flow MIR
  → verified optimization passes
  → Backend contract
  → LLVM IR / object / link
```

每层必须具备：

- 明确输入、输出和不变量；
- 结构化错误与稳定调试打印；
- 独立 verifier；
- SourceMap/Span 回溯；
- 资源预算和取消；
- 差分、快照、fuzz 或属性测试；
- 规则 ID 到实现和测试的追溯。

LLVM 类型不得出现在 Source、Syntax、Semantic、HIR、MIR 的公共接口中。Runtime 不依赖 Compiler Frontend；工具只能消费公开 Driver、Query、Diagnostic 和 Metadata 契约。

### 5.3 查询和增量编译

- P1 先实现正确、可重复的全量编译；
- P2/P3 再基于稳定 ID 和纯查询引入内存增量与磁盘缓存；
- 查询结果必须由输入哈希、目标、工具版本、能力和环境声明共同确定；
- 缓存命中不能跳过 verifier、权限检查或版本校验；
- 增量结果必须与干净全量构建进行随机差分；
- 未证明收益的细粒度查询框架不得增加 P1 关键路径复杂度。

### 5.4 Runtime 原则

- 核心语言无强制 GC，Runtime 保持最小；
- 分配器、panic 策略和 async executor 可替换；
- Runtime ABI 版本化，启动、TLS、panic、线程、任务和 I/O 分层；
- `no_std` 和裸机属于扩展目标，不反向限制 1.0 主机开发体验；
- 可观测性通过稳定事件 Schema 接入，不在 Runtime 中绑定单一供应商。

## 6. 2026 技术基线

当前拟采用 Rust 1.97.1、LLVM 22.1.8、Unicode 17.0、WASI v0.3.1、LSP 3.18、SLSA 1.2 和 SPDX 3.0.1。版本、官方来源、核验时间和升级规则统一维护在 [2026 技术基线](../90-reference/2026-technology-baseline.md)，避免易变版本污染稳定语言规格。

原则：只采用正式稳定版本；RC 仅作兼容探针；版本升级必须通过构建、ABI、代码生成、安全、性能和回滚验证，不能以“最新版”为唯一理由。

## 7. 现行权威路径与迁移规则

[完整项目目录架构](../X-Lang完整项目目录架构与模块说明.md)已经冻结 `specs/` 为规范来源、根 `rfcs/` 为 RFC 工作区、`docs/decisions/` 为 ADR 来源。在新的迁移 ADR 获批前，本规格沿用该现行契约，不重新创建第二套可写入口。

```text
x-lang/
├─ specs/                   # 现行唯一规范性语言、ABI 和治理规则
├─ rfcs/                    # 语言、工具链和生态重大提案
├─ compiler/                # 编译器 Workspace
├─ runtime/                 # 最小运行时
├─ library/                 # core/alloc/std
├─ tools/                   # CLI、fmt、doc、LSP 等
├─ tests/                   # conformance、ui、integration、platform
├─ benchmarks/              # 版本化性能套件和原始结果 Schema
├─ docs/                    # 指南、架构、工程、参考和 decisions/
└─ research/                # 默认不进入 Workspace 的实验原型
```

`docs/10-language/` 只能保存非规范性教程和解释；`docs/50-rfcs/`、`docs/60-decisions/` 和根 `decisions/` 不再作为新的可写入口。现有母版中的重复目录描述属于待迁移内容，不能生成新的规范、RFC 或 ADR。

如果未来希望改用根 `spec/`、全部文档集中或其他布局，必须先在现行 `docs/decisions/` 中接受路径迁移 ADR。ADR 必须定义迁移映射、只读重定向索引、链接修复、工具扫描范围、审批主体和回滚方式；完成前 `specs/`、`rfcs/`、`docs/decisions/` 保持 canonical。

## 8. 计划中的命令契约

以下是目标命令，不表示当前已经可用：

| 命令 | 目标 |
|---|---|
| `x check --workspace` | 解析、名称、类型、Trait 和借用检查 |
| `x build --profile dev` | 可调试的增量开发构建 |
| `x build --profile release` | 经验证优化的发布构建 |
| `x run -- <args>` | 构建并运行单一二进制目标 |
| `x test --workspace` | 单元、文档、集成和符合性测试 |
| `x fmt --check` | 幂等格式检查，不修改文件 |
| `x doc --test` | 生成 API 文档并执行示例 |
| `x bench --suite core` | 运行版本化基准并输出原始数据 |
| `x spec check` | 检查规则 ID、链接、RFC/ADR 和测试追溯 |
| `x doctor --json` | 检测工具链、SDK、平台和权限问题 |

所有命令必须支持结构化诊断、明确退出码、取消和 `--json` 自动化输出。网络访问默认关闭或显式提示；离线构建不得因遥测、更新检查或 Registry 不可用而失败。

## 9. 代码与接口风格

### 9.1 X-Lang 用户代码原则

```x
fn load_config(path: &Path) -> Result<Config, ConfigError> {
    let text = fs.read_to_string(path)?
    let config = Config.parse(text)?
    return Ok(config)
}
```

- 所有权转移、失败、异步、I/O 和不安全边界必须可见；
- 默认不可变，使用局部 `mut` 明确可变范围；
- 公开函数签名完整，不依赖跨模块全局推断；
- 使用领域名，禁止无边界 `utils/common/shared`；
- 标准格式只有一种，项目不得重新定义基础布局风格。

示例语法只是方向性样例；正式 Token、分号、返回和方法调用规则必须由语法 RFC 决定。

### 9.2 编译器实现原则

- 领域模型不依赖 LLVM、OS、编辑器或 Registry；
- 每个阶段返回结构化结果，不使用裸字符串错误；
- Pass 前后运行 verifier，优化可独立关闭和二分；
- 优先清晰、可证明正确的实现，测量后再引入复杂缓存或并行；
- 不重复开发已有成熟组件，依赖引入需评估维护、许可证、安全和可替换性。

## 10. 测试与验证策略

完整测试矩阵、Fuzz/Sanitizer 条件、规则追溯和发布阻断条件统一定义在 [2026 质量与验证门禁](../30-engineering/x-lang-2026-quality-gates.md)。核心原则是：规则、实现和测试一一映射；增量与全量构建随机差分；每层 IR 有 verifier；安全、代码生成和编译器崩溃缺陷不能通过缩小官方语料范围规避。

## 11. 暂定性能与体验 SLO

SLO 候选统一维护在 [2026 质量与验证门禁](../30-engineering/x-lang-2026-quality-gates.md)。任何性能比较必须由 Benchmark RFC 冻结 reference implementation、工作负载、平台、版本、flags、统计方法和失败阈值；尚未测量时只能称候选指标。

## 12. 安全与供应链边界

具体 Always/Ask first/Never 边界维护在 [2026 质量与验证门禁](../30-engineering/x-lang-2026-quality-gates.md)。语言层不可放宽的底线是：最小权限、显式能力、不可信输入预算、Safe/unsafe 义务分离、供应链来源可查，以及 AI 或外部内容不能覆盖已批准规范和人工质量门禁。

## 13. 分阶段成功标准

### P0：决策与规范骨架

- 确认现行 `specs/`、`rfcs/`、`docs/decisions/` canonical path；如需改变，先接受并执行路径迁移 ADR；
- 语法、类型、错误、所有权、内存、并发、ABI 十二类阻塞问题均有 RFC；
- 选择 20 个代表性程序作为可观察语义样本；
- 规格、规则 ID 和测试清单可以由工具检查。

### P1：可信端到端核心

- Hello World 和最小 CLI 能完成 Source→MIR→LLVM→Link；
- Lexer/Parser 对任意输入不崩溃；
- HIR/MIR verifier 和最小解释器可运行；
- `x check/build/run/test` 在一个 Tier 1 主机闭环；
- 没有 Web、GUI、ML 或 AI 能力进入默认 Workspace。

### P2：安全语言与标准库

- 所有权、借用、Trait、错误、泛型和模式匹配规则闭合；
- `core/alloc/std` 支持真实中型 CLI；
- 符合性、fuzz、sanitizer、基准和文档测试持续运行；
- 先确定一个 Tier 1 实现主机；Windows、Linux、macOS 依据真实 CI、真机和发布能力分层晋级，不要求虚假同时稳定；
- “可复现”在同一 target 上要求字节级制品目标，在不同 target 间只要求规范行为和测试结果满足平台契约。

### P3：工程效率

- 包管理、锁文件、离线构建、LSP、格式化、文档和调试闭环；
- 经正确性验证后引入增量编译；
- C FFI 稳定子集和至少一个真实跨语言案例；
- Alpha/Beta 发布具备签名、SBOM、回滚和漏洞响应。

### P4：1.0

- CORE 无阻塞未决项；
- 安全、性能、兼容、供应链和平台证据完成；
- 至少两个连续候选版本没有严重语义漂移；
- 外部用户能够仅根据文档完成安装、开发、测试和发布；
- 所有“最优/领先”表述都能链接到限定场景和可复现实验。

### P5+：生态与研究

- WASI/Web、服务器框架、Python/Node/JVM、GUI、ML/GPU 分别立项；
- 每个领域独立版本、Owner、平台矩阵、威胁模型和退出条件；
- 没有稳定用户和第三方贡献前，只称“官方生态原型”；
- Research 连续两个里程碑无可验证进展时必须重新评审或归档。

## 14. 规格完成标准

本规格通过评审后，下一阶段才能开始架构决策和任务拆解。通过条件：

- [ ] 项目所有者确认目标用户、优先级和非目标；
- [ ] 认可“不追求无条件全维度第一，而追求可验证 Pareto 竞争力”；
- [ ] 认可 1.0 设计原则、RFC 候选集和延期能力；
- [ ] 认可模块化单体优先、6～10 个早期 Workspace 成员；
- [ ] 认可继续使用现行 `specs/`、`rfcs/`、`docs/decisions/`，除非先完成路径迁移 ADR；
- [ ] 认可性能与体验指标必须通过基准 RFC 才能成为承诺；
- [ ] 认可官方稳定版本优先于候选版和未经验证的新组件。

## 15. 待项目所有者确认的问题

1. 系统/服务端/CLI 是否确认为 1.0 首要场景？
2. 是否接受 Web、GUI、ML/GPU 和 AI Runtime 不进入 1.0 核心？
3. 是否接受核心无 GC，GC 仅作为后续隔离实验？
4. 是否接受先稳定 C ABI，而不承诺通用 C++ 或 X 动态 ABI？
5. 是否接受先做模块化单体，根据真实边界再拆 crate？
6. 是否继续使用现行 `specs/`、`rfcs/`、`docs/decisions/`，还是单独启动路径迁移 ADR？
7. 首个 Tier 1 实现主机优先 Windows、Linux 还是按现有 CI 资源决定？
8. 对外定位更偏“安全高性能系统语言”，还是“高效原生应用语言”？
