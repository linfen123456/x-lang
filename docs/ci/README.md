# X-Lang CI/CD 与发布门禁

CI 是治理约束的执行面：先验证文档与追溯，再验证代码、依赖、测试、制品和发布。所有 job 使用固定工具链、最小权限、可审计工件和确定性缓存；失败输出不含秘密。

文档阶段的最小门禁包括 Markdown 标题与链接检查、XLF/XLC/XLE 定义计数、追溯抽查和原始资料差异检查；进入编译器实现阶段后，再把这些检查固化为仓库内的 CI 命令。主干和发布分支不得通过跳过门禁解决红灯。

## 流水线分层

| 层级 | 触发条件 | 必做检查 | 失败处理 |
|---|---|---|---|
| 文档门禁 | 文档、规范、RFC、ADR 变更 | 标题与链接、术语、来源映射、状态与成熟度、原始资料只读 | 阻止合并；由文档 Owner 修正，不允许标记为“无关失败” |
| 快速门禁 | 每个 Pull Request | 格式化、静态检查、单元测试、compile-pass/fail、许可证与秘密扫描 | 阻止合并；同一提交修复并重新运行 |
| 完整门禁 | 合并主干、发布候选及按容量配置的计划任务 | 全平台构建、集成测试、Fuzz 冒烟、ABI、可复现构建、基准抽样 | 隔离回归提交；不得用扩大容差掩盖失败 |
| 发布门禁 | Nightly/Beta/Stable 候选 | 完整平台矩阵、安全扫描、SBOM、签名、安装/升级/回滚演练 | 候选版本作废；修复后产生新候选版本 |
| LTS 门禁 | LTS 补丁与生命周期评审 | 向后兼容、迁移、CVE、制品保留、灾难恢复与 EOL 通知 | 不满足支持承诺时不得发布或结束支持 |

## Pull Request 必备证据

每个变更必须说明它解决的规范或任务、受影响组件、风险、测试和回滚方法。编译器诊断变更需要诊断快照；语言语义变更需要正例、反例、边界案例及 RFC；ABI 与标准库变更需要兼容性测试；性能优化需要基线、环境、样本和统计口径。只有文档变化时，也必须确认没有把待决策内容写成稳定承诺。

审查顺序为正确性、可读性、架构边界、安全、性能。高风险变更至少由领域 Owner 与独立审查人共同批准；提交者不能单独批准自己的权限提升、签名、发布、沙箱或供应链变更。

## 缓存、制品与秘密

缓存键必须包含工具链版本、目标平台、Profile、Feature、锁文件摘要和相关 Schema/IR 版本。缓存命中不能跳过输入验证；发生不一致时优先丢弃缓存并完整重建。PR 产生的制品不得自动进入可信发布通道，发布制品必须从受保护分支在隔离环境重新构建。

CI 使用短期凭据和最小权限。Fork PR 默认无发布密钥、注册表写权限和生产网络权限；日志在上传前进行秘密和个人数据扫描。测试报告、崩溃转储和 Fuzz 输入按数据分类设置访问权限与保留期。

## Flaky 与紧急例外

Flaky 测试不能简单删除或永久忽略。确认非产品回归后，可隔离到带 Owner、缺陷号和到期日的队列；核心语义、安全、ABI、数据完整性测试不得隔离。紧急发布只能缩短非关键检查，不能绕过签名、来源验证、关键安全测试和回滚验证；例外复盘期限由事故级别和已具备的响应能力在批准记录中明确，不能预写尚无法保障的固定 SLA。

## 验收标准

- 每一类变更都能确定唯一门禁、Owner、输入、输出和失败升级路径。
- Stable 候选可追溯到源提交、工具链、依赖锁、测试结果、签名和制品摘要。
- 同一源码与锁定环境的重复构建结果满足可复现构建约定；差异必须有可解释字段。
- 能在不改源码的情况下撤销发布、停止分发并恢复上一已知良好版本。
