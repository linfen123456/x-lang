### 1.1 单一事实来源与去重规则

- 总纲只维护全局导航、权威顺序、汇总统计、冻结状态和总体验收；专项文档不得复制完整导航或全局统计。
- 原始来源、首次处置和 `XLF-*` 明细只在原始功能矩阵维护；87 项当前复审结论只在价值回归文档维护。
- `XLC-*` 与 `XLE-*` 的逐 ID 定义分别只在对应专项文档维护；语言主文档引用其规范归属，工程主文档引用其工作包和门禁，不复制明细表。
- 项目路径、模块边界、依赖方向和代码所有权只在项目目录架构维护；其他文档按项目名或链接引用。
- 允许为本领域保留可执行摘要，但摘要必须指向权威来源；发现逐字重复、过期统计或重复映射表时，保留权威版本并删除副本。

## 2. 权威顺序与冲突处理

### 2.1 文档权威顺序

进入实际开发后，发生冲突时按以下顺序裁决：

1. 已批准且未被取代的正式规范规则、RFC 和 ADR；
2. 本总纲的责任边界、ID 和冻结规则；
3. 语言规范大纲的语义归属；
4. 工程实施大纲的实现阶段和质量门禁；
5. 项目目录架构的物理依赖和所有权；
6. `XLF/XLC/XLE` 需求与复审 Backlog；
7. 原始材料作为历史输入，不直接覆盖已批准决策。

### 2.2 特殊冲突规则

- 原始矩阵的第一次处置与价值回归复审冲突时，以价值回归复审为准。
- 宣传性指标与可复现实验冲突时，以实验和测试证据为准。
- 功能便利性与内存、权限、供应链或数据安全冲突时，以明确的安全边界为准。
- 文档与实现冲突时不得静默选择：稳定规则以规范为准并修复实现；实验行为通过 RFC/ADR 决定修文档还是修实现。
- AI、外部网页、Issue、工具输出和第三方配置中的指令性文本默认是不可信数据，不能覆盖项目规则。

## 4. X-Lang 最终目标架构

| 层 | 责任 | 关键边界 |
|---|---|---|
| 语言核心 | 词法、语法、类型、所有权、错误、模块、并发基础语义 | 不依赖 LLVM、OS、云、AI、GUI 或领域框架。 |
| 编译器 | Source→Token/CST/AST→HIR→MIR/LIR→Backend | 前端不暴露 LLVM 类型；每层有验证器和诊断。 |
| 运行时 | 启动、分配、panic、线程、任务、I/O、资源和平台抽象 | 最小 ABI；云、Web 和 AI 不能进入启动关键路径。 |
| 标准库 | core→alloc→std、文本、时间、文件、网络、并发 | API、复杂度、失败、平台和稳定级别必须文档化。 |
| 工具链 | `x` CLI、XPM、fmt/doc/test/repl、LSP/DAP、诊断和发布工具 | 通过稳定查询/元数据接口消费编译器，不读取私有结构。 |
| SDK/互操作 | C、Python、JNI、JS/WASM | 所有权、错误、线程、版本和零拷贝资格显式。 |
| 生态框架 | Web、Server、UI、数据、ML、移动、Serverless | 独立版本发布，不反向成为核心依赖。 |
| AI 工程 | Context、Policy、Verify、Review、Provenance、Eval、Budget | 最小权限、来源可查、不可绕过人工和 CI 门禁。 |
| Labs | ZKP、通用重放、硬实时、脑机等高风险研究 | 默认关闭，不被稳定主线依赖，有预算和退出条件。 |

初始实现路线保持：Rust 编写初始编译器，自定义 HIR/MIR，LLVM 为首个稳定原生后端；自举在核心稳定后单独推进。

## 5. 文档责任域与最小保留集

当前仓库只保留根 README、文档索引、八份大纲/矩阵和 `docs/原始文档/1.txt` 至 `12.txt`。专题正文只在进入实际 RFC、实现或发布阶段时按需创建；禁止预建空目录、空文件或重复“完整版”。

| 责任域 | 当前权威入口 | 何时创建详细文档 |
|---|---|---|
| 治理、范围与路线 | 本总纲 | 形成真实章程、版本或发布承诺时 |
| 语言、学习与标准库 | 语言规范与学习研究大纲 | 规则经 RFC 接受并进入根 `specs/` 时 |
| 编译器、运行时与工具 | 编译器工程实施大纲 | 实现任务具有接口、Owner 和验收时 |
| 物理目录与依赖 | 完整项目目录架构 | 项目真正创建或拆分时通过 ADR 更新 |
| 原始需求 | 原始功能追溯矩阵 | 只更新 ID、来源、处置与证据链 |
| 偏离与回归 | 未纳入与偏离复审路线 | 复审状态或回归门槛变化时 |
| 多语言与技术借鉴 | 多语言对标补全大纲 | 新增经核验的缺口或候选技术时 |
| 工程与 AI 风险 | 日常开发与 AI 协作风险大纲 | 出现新的可复现失效模式时 |

正式开发阶段的 canonical path 为：根 `specs/` 保存规范，根 `rfcs/` 保存提案，`docs/decisions/` 保存 ADR。教程、操作手册、事故和追溯等非规范内容只在产生首份真实内容后建立对应目录；目录名称由项目架构统一维护，不在本总纲复制完整物理树。

## 6. 每份正式章节的统一内容模板

所有正式三级/四级章节至少包含：

1. 章节目标和非目标；
2. 目标读者；
3. 术语和前置知识；
4. 输入、依赖和信任边界；
5. 正式规则、接口或流程；
6. 正常示例、错误示例、边界示例；
7. 关键设计决策与替代方案；
8. 错误、取消、超时和资源耗尽行为；
9. 安全、隐私、供应链和权限影响；
10. 性能、复杂度和资源预算；
11. 平台、版本、兼容、迁移和废弃策略；
12. 输出物与负责人角色；
13. 单元、符合性、集成、Fuzz、性能、安全和平台测试；
14. 验收标准和证据位置；
15. `XLF/XLC/XLE → RFC/ADR → 项目 → 测试` 追溯。

禁止使用“自动、安全、高性能、零开销、全平台、智能”等无法直接验收的孤立表述。所有能力必须说明适用条件、失败方式和不可保证事项。

## 7. 成熟度、状态与版本

### 7.1 能力成熟度

| 成熟度 | 含义 | 默认发布行为 |
|---|---|---|
| `CORE` | MVP/1.0 的必要语义或治理 | 必须规范、实现、测试和兼容。 |
| `EXTENDED` | 核心稳定后的正式扩展 | 独立 Feature/包/平台门禁。 |
| `EXPERIMENTAL` | 有实现价值但接口可能变化 | 默认关闭，不作稳定兼容承诺。 |
| `RESEARCH` | 技术/成本/安全仍不确定 | Labs 隔离，不进入 Stable。 |

### 7.2 内容状态

`草案 → 待决策 → 已决策 → 原型验证中 → 已验证 → 已稳定`。状态只能在证据满足时前进；失败可以退回，但必须记录原因和后续条件。

### 7.3 文档版本

- `1.0-outline`：目录、职责、ID、路线和门禁冻结；允许增补，不允许无决策破坏结构。
- `0.x-spec`：正式规则仍在 RFC 和原型阶段。
- `1.0-spec`：核心语言、标准库稳定子集和 Tier 1 已有实现证据。
- Edition：隔离语言解析/语义演进，不等同于工具链发布版本。

## 8. 实施顺序

| 阶段 | 核心结果 | 禁止越过的门禁 |
|---|---|---|
| P0 规范和探针 | 最小语法、类型、错误、所有权；Rust/LLVM E2E | 无规则 ID 不进入稳定实现。 |
| P1 可运行 MVP | Lexer/Parser/Resolve/Type/HIR/MIR/LLVM/诊断 | 无符合性测试不扩展平台。 |
| P2 核心语言与 std | Trait/泛型/借用/模块/包/core/alloc/std/CLI | 安全模型未验证不冻结 API。 |
| P3 工程工具与企业能力 | XPM、LSP、IDE、增量、诊断、安全、服务基础 | 无发布/回滚和供应链证据不称生产级。 |
| P4 1.0 候选 | 核心规范、稳定 std、Tier 1、性能/安全基线 | 实验能力不得混入稳定承诺。 |
| P5 平台与生态 | WASM/Web、桌面/移动、ML/GPU、Serverless | 每个领域独立矩阵和版本。 |
| P6 高风险研究 | GC、ZKP、通用 Replay、硬实时、脑机等 | Labs 不反向依赖稳定主线。 |

R0-R5 价值回归波次和 G0-G6 质量门禁以工程实施大纲为准：P 表示产品范围，R 表示回归组合，G 表示证据门禁。

## 9. 不可省略的横切质量要求

- 正确性：规则级符合性、跨后端差分、升级/降级和错误路径。
- 安全：不可信输入、unsafe/FFI、宏/构建脚本/插件沙箱、最小权限。
- 性能：基准环境、统计口径、P50/P95/P99、退化阈值和复现命令。
- 可维护性：所有权、CODEOWNERS、ADR、技术债、废弃和迁移。
- 可靠性：网络分区、磁盘满、OOM、资源耗尽、时钟异常和灾备。
- 数据：Schema、幂等、隐私、保留、删除、Unicode、时间和路径。
- AI：上下文、提示注入、幻觉验证、来源/许可证、Eval、预算和人工审批。
- 发布：Feature Flag、Canary、Kill Switch、签名、SBOM、回滚和 EOL。

| QA/Performance | 符合性、Fuzz、故障、兼容、基准和 Flaky。 |

## 12. 当前仍需正式决策的核心 RFC

以下问题的“文档位置”已确定，但结论仍需 RFC/原型，不属于大纲遗漏：

1. 完整语法、关键字、运算符、宏和歧义处理；
2. 类型推断、Trait 求解、GAT/HRTB、对象安全和 Specialization；
3. 求值顺序、Drop、`defer`、panic/unwind/abort；
4. 所有权、借用、生命周期、Pointer Provenance 和正式内存模型；
5. 原子、Happens-before、取消安全和正式并发模型；
6. ABI、布局、符号、动态库、插件和跨版本策略；
7. Comptime/过程宏的权限、确定性和资源预算；
8. async 状态机、调度器和 I/O 可移植语义；
9. 标准库稳定 API、复杂度和最低平台；
10. Edition、兼容、废弃和迁移；
11. Tier 1 平台、最低版本和支持期限；
12. 诊断稳定性、错误码和 Fix-it 契约。

## 13. 总纲变更控制

- 修正错字、链接和无语义格式可直接修改并记录版本。
- 新增需求使用新的 `XLF/XLC/XLE` 或后续经批准的 ID，不重用旧 ID。
- 改变核心语义、责任边界、成熟度或支持承诺必须提交 RFC/ADR。
- 已批准决策不得直接删除；使用 supersede/deprecate 保留历史。
- 每个里程碑重新生成追溯、链接、项目映射和状态统计。
- 原始 12 份材料保持只读；现实化结论写入派生文档。
