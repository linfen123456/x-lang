# ADR-0005 查询式编译器与无损 CST

> 状态：Accepted｜版本：2.1.0｜负责人：Compiler Lead｜最后更新：2026-10-22
> 类型：ADR｜新增（v2）

## 背景

增量编译、LSP、格式化、MCP 都要求：保留注释、能按需重算、能取消。批处理式编译器事后再改造成本很高【推断：业界经验】。

## 决策

1. **P0 起使用无损 CST**：Lexer 保留 trivia（空白、注释），Parser 带错误恢复，生成不可变的绿树/红树结构。AST 是建立在 CST 之上的类型化视图。实现：**采用 `rowan` =0.17.0**（[ADR-0008](ADR-0008-pre-kickoff-decisions.md) K4），只能在 `syntax::tree` 门面内引用。
2. **P1 起编译器是查询式的**：每个阶段都是 `query(key) -> value` 形式的纯函数，带依赖追踪和内存缓存，支持取消。实现：**采用 `salsa` =0.28.5**（K4），只能在 `driver::db` 门面内引用。P1 开工的第一周做一次验证探针，要求覆盖 [compiler](../design/compiler.md) §3 的查询清单，并支持取消。如果探针失败，就在门面后面换成自研薄层（依赖追踪 + revision 计数 + 内存 memo），门面以外的代码不需要改动。
3. **P3 起支持落盘缓存**：在门面层按内容哈希缓存 Item 级产物（签名、MIR、对象文件），不依赖 `salsa` 自身的持久化能力；并且必须满足“增量编译结果与全量编译结果一致”的差分门禁。
4. 查询的粒度：每个文件、每个 Item、每个函数体。函数体内部的修改不得导致其他函数体重新做类型检查（签名没有变化时）。

## 后果

- P0 的 Parser 工作量比只生成 AST 时略多【推断：约 +2 周】，但避免了 P1/P3 重写 Parser 和 Driver。
- 所有阶段都不得读写全局可变状态。这一点由代码评审保证，并用“二次运行查询零重算”的测试验证。
