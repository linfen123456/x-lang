# ADR-0002：阶段化模块化单体架构

## 状态

Proposed

## 日期

2026-08-18

## 背景

X-Lang 当前只有文档、候选 RFC 和 ADR，没有编译器实现。长期能力地图包含编译器、运行时、标准库、工具链、Web、UI、AI 和多语言互操作；如果按长期地图提前建立大量 crate 或仓库，会在接口、消费者和性能证据出现前制造依赖、版本和维护成本。反过来，将全部代码永久放入一个无边界项目，又会妨碍测试、隔离和后续演进。

## 决策

采用“阶段化模块化单体”：逻辑边界从第一天存在，物理拆分由阶段和证据驱动。

### D0 文档阶段

- 只保留大纲、原始材料、真实 RFC 和 ADR；
- 不创建空 `specs/`、空 crate、空服务或未来目录；
- `Proposed` 只表示候选，不表示已经实现。

### P0/P1 可运行核心

Rust Workspace 使用 4～6 个成员，推荐初始成员为：

```text
compiler
runtime
cli
library-core
conformance
```

`compiler` 内部按 `source → syntax → semantic → ir → codegen → driver` 分层；LLVM 只出现在 codegen 适配层。格式化、最小 XPM 和构建编排先作为现有成员的内部模块或 `x` 子命令，不为未来消费者预拆项目。

### P2–P4 工程化

内部模块只有同时具备明确契约、测试和回退方案，并至少满足下列一项时，才能拆为独立 crate 或项目：

- 两个以上稳定消费者；
- 独立发布或兼容周期；
- 进程、权限或第三方依赖隔离；
- 可复现的增量编译收益；
- 独立平台构建需求；
- 长期独立 Owner。

### P5+ 联邦生态

Web、UI、Server、SDK、AI 和 ML 使用独立版本与发布门禁，只依赖核心公开 API，不读取编译器私有 AST/HIR/MIR，也不能成为核心构建依赖。

## 依赖规则

- 核心编译链依赖单向流动，底层模块不得依赖 driver、CLI 或 IDE；
- 标准库不得依赖包管理器、LSP、Web 或云服务；
- 工具通过稳定查询、诊断和工件契约消费编译器能力；
- Labs 默认关闭，稳定主线不得依赖 Labs；
- 目录名称不构成拆分理由，`x-*` 需求目标首先映射到现有责任域。

## 替代方案

### 从第一天拆分完整 Monorepo

拒绝。没有消费者和实现证据时，拆分只会固化猜测并扩大循环依赖、版本协调和构建成本。

### 永久单 crate

拒绝。编译器、运行时、CLI、核心库和符合性测试具有不同依赖及发布责任；永久混合会破坏隔离和测试边界。

### 每个领域立即建立独立仓库

拒绝。Web、AI、ML 等生态尚未具备稳定核心 API，提前建仓会产生空接口并反向影响语言设计。

## 后果

### 正面

- P0 可以尽快形成 Source 到可执行文件的纵向链路；
- 逻辑边界可测试，但不提前支付多项目协调成本；
- 物理拆分有明确证据和回退门禁；
- 实验生态不能污染核心语言和工具链。

### 代价

- 初期 `compiler` 内部模块必须严格执行依赖检查；
- 后续拆分需要迁移路径和契约测试；
- 目录架构文档必须持续区分真实目录与长期能力地图。

## 接受门禁

- P0 Workspace 方案能在 4～6 个成员内完成最小纵向链路；
- 模块依赖图无环，LLVM 不泄漏到前端接口；
- 至少一个候选拆分用消费者、隔离或构建测量证明必要性；
- 每个拆分门禁具有自动检查和合回单体的回退方案；
- 与 RFC-0003/0004 的 XPM/XBuild 阶段边界一致。
