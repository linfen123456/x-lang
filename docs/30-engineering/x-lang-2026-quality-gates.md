# X-Lang 2026 质量与验证门禁

> 状态：草案
> 责任角色：规范、编译器、运行时、测试、安全、发布工程
> 最后更新：2026-08-17
> 上游依据：[X-Lang 2026 设计规格](../00-governance/x-lang-2026-design-spec.md)

本文件定义 X-Lang 从设计目标进入稳定承诺前必须提供的证据。指标均为基准 RFC 的候选输入，尚未测量前不得作为产品宣传。

## 测试矩阵

| 层级 | 必须验证 |
|---|---|
| 规范测试 | 每条 CORE 规则至少一个 pass、fail 和边界案例 |
| Lexer/Parser | 任意字节输入不崩溃；恢复稳定；parse/print 往返 |
| Semantic | 类型、Trait、Borrow 的规则级与属性测试 |
| HIR/MIR | verifier、文本往返、reducer、解释器/后端差分 |
| Codegen | LLVM IR 验证、ABI、汇编、链接和目标差分 |
| Runtime/Std | sanitizer、参考解释、压力、故障注入和平台测试 |
| Tooling | CLI 快照、LSP/DAP 协议、取消、超时和大型项目延迟 |
| Supply chain | 锁文件、离线、签名、SBOM、可复现和撤回演练 |
| Release | 干净机安装、升级、回滚、N-1 兼容和已知问题验证 |

## 发布质量门禁

- CORE 规则追溯覆盖率必须达到 100%；
- 正式内存模型覆盖范围内，Safe X 的已知 soundness 缺陷阻断发布；
- Parser、宏、包清单、对象和调试信息读取等不可信输入面必须持续 fuzz；
- 发布候选版必须在 Fuzz RFC 规定的平台、sanitizer、最小时长和覆盖指标下没有未归档崩溃；
- 外部输入触发的 Compiler Crash 均进入阻断级分诊，不能用“不在官方语料中”排除；
- 增量与全量构建随机差分必须等价；
- 优化前后使用 MIR 解释、后端差分和属性测试验证；
- 性能回归阈值按领域定义，不能用平均值掩盖尾延迟或内存退化；
- 每个 soundness 或代码生成缺陷记录受影响版本、最小复现、根因和修复验证。

## Safe X 最小覆盖门禁

1.0 的正式内存与并发模型至少必须覆盖：

- 初始化、未初始化读取和部分初始化；
- 对象生命周期、移动、复制、析构和存储复用；
- 共享/独占别名、重借用和 Pointer Provenance；
- 对齐、布局、Padding、越界和整数到指针转换；
- unsafe 操作的调用者义务与实现者义务；
- 原子读写、内存序、Happens-before 和数据竞争；
- panic、取消、unwind/abort、线程退出和 FFI 边界的清理；
- 编译器优化可依赖的全部有效性不变量。

覆盖清单和 UB 分类表必须接受完备性审查；每类规则必须具有 compile-pass/fail、MIR 解释/后端差分或模型测试。并发模型必须包含 litmus tests 和有界 model-check。未覆盖语义必须标为 unsafe、实验或未稳定，不能进入 Safe X 的稳定结论。

## 平台 Tier 与可复现门禁

每个 target 的机器可读平台条目必须包含：

- 精确 target triple、CPU 特性基线、ABI 和 Endianness；
- OS、最低版本、libc/CRT、SDK、linker 和系统库版本；
- 编译器、标准库、Runtime、构建工具和依赖锁；
- CI、真机、签名、安装、调试和发布证据；
- Tier 等级、支持范围、降级行为、阻断条件和退役流程。

同 target 字节复现只在 source、依赖、flags、toolchain、SDK、linker、locale、timezone、环境变量、时间戳策略和链接输入全部固定时评估。不同 target 不要求字节相同，只要求满足各自平台契约与规范可观察行为。不可避免的签名、时间戳或平台元数据必须列入可审计例外，剥离后内容仍需可比较；无法解释的差异阻断发布。

## 性能与体验候选 SLO

- 编辑后诊断 P95：参考 100k LOC 工作区小改动不超过 200 ms；
- LSP 输入响应 P95：不超过 100 ms，长任务必须可取消；
- 原生计算基准：相对 Benchmark RFC 冻结的 C/Rust reference implementation 评估；
- 服务尾延迟：与同算法、同依赖、同安全设置对照，P99 退化不得被吞吐平均值掩盖；
- 发布回归：任何核心基准超过批准阈值必须阻断、回退或形成有期限豁免；
- 诊断质量：常见错误测试中，首条诊断定位根因的比例目标至少 85%。

Benchmark RFC 必须固定：程序、数据集、参考实现、编译器与依赖版本、flags、硬件、OS、预热、样本数、统计方法、失败阈值、原始结果格式和复现命令。

## 新手体验实验

至少邀请 20 名符合目标画像且未参与语言设计的用户完成统一任务：

1. 安装或选择已安装工具链；
2. 创建 CLI 项目并解析参数；
3. 读取配置文件并处理缺失或格式错误；
4. 编写至少一个单元测试和一个失败用例；
5. 生成 release 制品；
6. 在无网络环境使用锁文件重新构建。

实验必须记录参与者画像、允许材料、求助规则、时限、首次成功率、失败阶段和诊断是否可操作。首次成功率候选目标为 80%，但正式阈值需在试运行后由体验 RFC 批准。

## 安全与供应链边界

### 始终执行

- 不可信输入在边界验证并设置大小、时间和内存预算；
- Safe/unsafe、FFI、宏、构建脚本、插件和 Registry 分别建立威胁模型；
- 依赖锁定、签名、来源证明、SBOM 和可复现构建进入发布门禁；
- AI 生成内容必须产生 diff、来源记录和验证证据；
- 权限默认最小化，网络、文件、环境和进程能力显式授予。

### 必须先经过 RFC/ADR 和人工确认

- 改变核心可观察语义、内存模型或 ABI；
- 新增关键字、内置属性、隐式转换或新的不安全逃生口；
- 引入新的编译器后端、增量数据库或链接器；
- 添加默认联网、遥测、远程缓存或自动执行第三方代码；
- 把实验能力提升为 Stable。

### 永远禁止

- 提交密钥、生产凭据或未脱敏用户数据；
- 为通过测试而删除失败用例、降低安全门禁或隐藏平台失败；
- 让文档、AI 输出或外部内容静默覆盖已批准规范；
- 让 CORE 反向依赖 Ecosystem、AI、ML 或 Research；
- 在没有复现实验时使用“零成本”“最快”“完全安全”或“全面优于”。

## 证据记录要求

所有质量结论必须记录：目标版本、规则或需求 ID、环境、命令、原始数据、结果摘要、失败与豁免、负责人角色和复核日期。豁免必须有到期日，过期后自动恢复阻断状态。
