# X-Lang 文档中心

本文件是 X-Lang 文档的统一入口，也是文档分类、命名、状态和维护规则的单一事实来源。

仓库当前处于架构与文档基线阶段。`docs/` 根目录中的八份 `X-Lang*.md` 文件是已经冻结结构的顶层母版；后续内容应按领域拆分，不再继续向根目录堆放同级文件。

现行 canonical path 以已冻结项目架构为准：规范写入根 `specs/`，RFC 写入根 `rfcs/`，ADR 写入 `docs/decisions/`。其他目录只能提供解释或索引，不得建立第二份可写权威正文。路径变更必须先通过 `docs/decisions/` 中的迁移 ADR。

## 文档架构

文档采用“入口 → 治理 → 领域 → 决策 → 交付 → 历史”的分层方式。随着项目增长，新增内容按下面的目标结构归档：

```text
docs/
├─ README.md                         # 文档总入口与维护规则
├─ X-Lang*.md                        # 顶层母版；仅保留现有八份
│
├─ 00-governance/                    # 项目章程、目标、术语、治理和路线图
│  ├─ project-charter.md
│  ├─ goals-and-non-goals.md
│  ├─ glossary.md
│  ├─ roadmap.md
│  └─ rfc-process.md
│
├─ 10-language/                      # 非规范性语言指南、示例和迁移解释
│  ├─ guide/                         # 非规范性教程和学习路线
│  ├─ examples/                      # 可运行、可测试的文档示例
│  └─ compatibility/                 # Edition、版本和迁移规则
│
├─ 20-architecture/                  # 系统总体架构和边界
│  ├─ compiler/
│  ├─ runtime/
│  ├─ standard-library/
│  ├─ tooling/
│  └─ interoperability/
│
├─ 30-engineering/                   # 实施、开发环境和工程流程
│  ├─ getting-started/
│  ├─ build-and-ci/
│  ├─ testing/
│  ├─ security/
│  └─ release/
│
├─ 40-ecosystem/                     # 包管理、IDE、Web、数据、AI 等生态
│  ├─ package-management/
│  ├─ editors/
│  ├─ web-and-services/

│  ├─ README.md                      # ADR 索引与状态表
│  └─ NNNN-short-title.md
│

│  └─ completed/                     # 已完成，仅保留结果与复盘
```

目录按两位数字排序，数字只表达导航顺序，不表达模块依赖。目录应在出现第一份实际文档时创建，不提交仅用于占位的空目录。

## 内容放置决策

新增文件前，按下列顺序判断：

1. 改变语言可观察语义或稳定生态契约：放入根 `rfcs/`，批准后同步根 `specs/`。
2. 记录已经作出的、代价较高的工程选择：放入 `docs/decisions/`。
3. 描述正式语言规则：放入根 `specs/`；`docs/10-language/` 只作非规范性解释。
4. 描述如何学习或使用：放入 `10-language/guide/`。
5. 描述组件边界与内部接口：放入 `20-architecture/` 的对应领域。
6. 描述开发、测试、构建、安全或发布流程：放入 `30-engineering/`。
7. 描述带期限、负责人和验收条件的工作：放入 `70-plans/current/`。
8. 描述尚未承诺的假设或实验：放入 `80-research/`。
9. 纯索引、矩阵和稳定查询资料：放入 `90-reference/`。

如果一份文件同时覆盖多个类别，应确定唯一主职责，将正文放入主目录，其他领域只添加链接，不复制正文。

## 文档类型与边界

| 类型 | 回答的问题 | 必须包含 | 不应包含 |
|---|---|---|---|
| 总纲/索引 | 去哪里找权威内容 | 范围、链接、状态 | 重复的完整正文 |
| 规范 | 程序必须如何解释 | 规则、正反例、诊断、测试映射 | 未标记的设想 |
| 指南 | 用户如何完成任务 | 前置条件、步骤、可运行示例 | 新的规范性语义 |
| 架构 | 组件如何划分与协作 | 职责、非职责、接口、依赖 | 临时任务清单 |
| RFC | 是否引入一项重大变化 | 背景、方案、备选、影响、迁移 | 未经批准即宣称已稳定 |
| ADR | 为什么选择当前工程方案 | 背景、决策、备选、后果 | 删除被替代的历史决策 |
| 计划 | 谁在何时交付什么 | 范围、负责人、里程碑、验收 | 永久性的规范事实 |
| 研究 | 某个假设是否成立 | 假设、方法、数据、结论、退出条件 | 稳定兼容承诺 |
| 参考 | 已确定信息如何快速查询 | 来源、版本、结构化数据 | 大段论证过程 |

## 文件命名规则

- 目录和新增文件统一使用小写英文 `kebab-case`，例如 `borrow-checking.md`。
- RFC 和 ADR 使用四位编号：`NNNN-short-title.md`，编号一经分配不得复用。
- 顶层八份冻结母版和 `原始文档/` 保持现名，不做无收益的批量改名。
- 同一主题只允许一个权威文件，禁止出现 `最终版`、`最新版`、`新新版本`、`副本` 等名称。
- 临时笔记不得直接提交到 `docs/` 根目录；需要保留时转成计划、研究记录、RFC 或 ADR。
- 图片等资源放在所属文档旁的 `_assets/` 中，名称应表达内容而不是截图序号。

推荐：

```text
../specs/language/ownership-and-borrowing.md
../rfcs/0001-module-system.md
decisions/0001-use-rust-for-bootstrap-compiler.md
```

不推荐：

```text
docs/新语言设计最终版2.md
docs/杂项.md
docs/临时记录.md
docs/架构副本.md
```

## 文档头部元数据

除 README、索引和原始材料外，新文档应在标题后包含以下最小元数据：

```markdown
# 标题

> 状态：草案
> 责任角色：编译器前端组
> 最后更新：YYYY-MM-DD
> 上游依据：XLF-001、RFC-0001
> 相关模块：compiler/x-parser
```

允许的状态为：

- `草案`：内容正在形成，不能作为稳定依据；
- `评审中`：范围已基本完整，正在接受审查；
- `已批准`：已通过对应治理流程；
- `已实现`：批准内容已经有实现和验证证据；
- `已稳定`：进入兼容性承诺；
- `已废弃`：仍保留历史，但不推荐新增使用；
- `已取代`：必须链接到替代文档。

## 文档维护规则

### 单一事实来源

- 需求原文与 `XLF-*` 定义以原始功能追溯矩阵为准。
- `XLC-*` 和 `XLE-*` 分别以对应补全大纲为准。
- 当前复审结论以未纳入与偏离内容复审文档为准。
- 正式语言行为以根 `specs/` 和已批准的根 `rfcs/` 为准。
- 工程选择以 `docs/decisions/` 中的有效 ADR 为准。
- 物理模块、依赖方向和所有权以项目目录架构为准。

其他文档只能摘要并链接权威来源；如果摘要与权威来源冲突，应修正摘要而不是建立第二套规则。

### 一份文档一个职责

- 文件标题应能准确概括其唯一主职责。
- 超过约 500 行或同时包含三个以上独立主题时，应评估拆分。
- 拆分后保留索引页，说明阅读顺序和各子文档边界。
- 不按“想到什么写什么”的时间顺序组织长期文档。

### 链接与追溯

- 优先使用相对链接，确保仓库克隆后仍可导航。
- 正式规则应逐步形成 `需求 ID → 规范/RFC → ADR → 模块 → 测试 → 发布` 链路。
- 文档移动时必须同步更新入链；没有自动检查前，可使用 `rg` 搜索旧路径。
- 引用外部资料时记录标题、版本或访问日期，避免只保存易失效链接。

### 更新与删除

- 行为或架构发生变化时，文档更新应与实现变更在同一提交或同一变更集中完成。
- ADR 和已批准 RFC 不直接删除；发生变化时标记为“已取代”，并链接新记录。
- 临时计划完成后移入 `70-plans/completed/`，保留结果和偏差复盘。
- 失去价值且不承担历史证据的重复草稿可以删除，Git 历史负责保存恢复路径。
- `原始文档/` 默认只读；若发现问题，通过追溯或勘误文档记录，不改写原文。

## 新增文档检查清单

提交前确认：

- [ ] 文件位于正确领域目录，而不是随手放在 `docs/` 根目录；
- [ ] 标题、文件名和主职责一致；
- [ ] 已搜索现有文档，不存在另一个权威正文；
- [ ] 状态、责任角色、日期和上游依据完整；
- [ ] 规范性结论具有需求、RFC 或 ADR 依据；
- [ ] 使用相对链接，并验证所有本地链接目标存在；
- [ ] 示例明确标注是否可运行，未来具备测试时纳入文档测试；
- [ ] 没有把规划中的模块描述成已经实现；
- [ ] 更新了本页或所属子目录的索引；
- [ ] 没有修改 `原始文档/` 的历史内容。
