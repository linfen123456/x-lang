## 原始材料

`原始文档/1.txt` 至 `原始文档/12.txt` 是历史输入，保持原貌，只用于追溯。它们不是当前规范，不能覆盖已批准的规范、RFC 或 ADR。

## 权威顺序

进入实际开发后，冲突按以下顺序处理：

1. 已批准且未被取代的正式规范、RFC 和 ADR；
2. 企业级完整文档体系总纲；
3. 语言规范大纲；
4. 编译器工程实施大纲；
5. 完整项目目录架构；
6. `XLF/XLC/XLE` 矩阵与复审路线；
7. 原始材料。

当前尚未创建正式规范目录。需要时采用现有架构约定：根 `specs/` 保存规范，根 `rfcs/` 保存提案，`docs/decisions/` 保存 ADR；没有首份实际内容时不创建空目录。

## 最小维护规则

- `docs/` 根目录不再新增新的 `X-Lang*.md`，除非总纲明确批准新的权威大纲；
- 新结论优先更新对应大纲，不另建“最终版”“最新版”“补充版”文件；
- 一项事实只在一个文件维护，其他文件使用相对链接；
- 原始材料默认只读；勘误写入追溯矩阵；
- 性能数字记录环境、版本、数据和复现命令；没有证据时只写研究目标；
- 目录树是长期能力地图，不等于必须立即创建的 crate 清单；
- Web、GUI、ML、GPU、AI 和研究能力不能反向成为核心语言依赖；
- 文档移动或删除后检查全部相对链接；历史内容由 Git 保存，不保留重复归档副本。

## 新内容放置

| 内容 | 放置位置 |
|---|---|
| 语言可观察语义 | 根 `specs/`，且必须有批准 RFC |
| 重大语言或生态提案 | 根 `rfcs/` |
| 工程架构决策 | `docs/decisions/` |
| 大纲级范围或路线调整 | 更新对应现有大纲 |
| 原始需求处置 | 更新追溯矩阵或复审路线 |
| 临时研究 | 先记录 Issue/任务；形成稳定结论后归并大纲或 RFC |

未经批准的临时分析不作为长期文档提交，避免再次形成重复权威来源。
