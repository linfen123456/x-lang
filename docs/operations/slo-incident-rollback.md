# SLO、事故响应、回滚与灾备

## SLI/SLO 候选基线

当前没有上线服务和运行数据，下表只定义指标与门禁性质，不构成 SLO/SLA 承诺。每个服务上线前通过 RFC 根据用户影响、团队值守、观测窗口和实测基线填写目标与告警；没有 Owner、数据和错误预算策略时不得发布数字。

| SLI | 候选目标填写方式 | 门禁性质 |
|---|---|---|
| 编译/制品服务可用性 | 按服务窗口记录成功率和排除项 | 目标和燃烧率由服务 RFC 批准 |
| 编译延迟 | 固定语料的 P50/P95/P99 与版本基线差异 | 连续窗口回归才告警，阈值由基准证据决定 |
| 失败可诊断率 | 能关联 run/trace/artifact ID 的失败占比 | 严重事故缺少关联 ID 必须复盘 |
| 签名/供应链验证 | 所有进入可信通道的制品必须验证 | 任意绕过或不匹配立即阻断，不以百分比稀释 |

SLO 只对声明的 Tier、版本和工作负载有效；没有数据的目标保持候选且不进入营销材料。错误预算耗尽时冻结非必要变更，优先修复可靠性和回归。

## 事故流程

1. 值班人确认影响、建立 `INC-YYYYMMDD-NNN`，冻结高风险发布并保护证据。
2. 按服务 RFC 规定的响应窗口分级：SEV-1 数据损坏/安全/大范围不可用；SEV-2 关键能力退化；SEV-3 局部或可绕过。尚无值班能力的服务不得虚构分钟级响应承诺。
3. 指派 Incident Commander、技术负责人、沟通负责人和记录人；更新频率由级别和沟通计划规定并记录。
4. 先止血（kill switch、限流、降级、隔离），再定位；不在事故中直接做大重构。
5. 恢复后验证 SLO、数据完整性、签名和回滚结果；SEV-1/2 的复盘期限由事故政策批准并对外/对内明确，不在项目尚未配备响应团队时预写固定天数。

## 回滚与灾备

代码/制品回滚优先使用上一签名版本；数据库采用 Expand→Migrate→Contract，回滚前先验证 N-1 读写兼容。数据恢复必须校验哈希、顺序、幂等键和权限，禁止以恢复覆盖原始证据。

| 资产 | RTO/RPO 决策依据 | 最低恢复验证 |
|---|---|---|
| 发布制品/签名/SBOM | 不可变副本、签名密钥恢复和发布影响；是否允许丢失任何已确认发布由 RFC 明确 | 摘要、签名、来源与下载端一致 |
| 注册表元数据 | 写入频率、备份间隔、撤回/恢复责任和用户影响 | 顺序、版本、权限、哈希和 N-1 客户端 |
| 研究数据 | 可重建成本、数据权利、预算和保留政策 | 授权、删除、数据集版本与复现替代 |

每个资产在上线/晋级前必须由 Owner 提交具体 RTO、RPO 和演练频率并用首次恢复演练校准。灾备演练必须注入区域不可用、密钥轮换、损坏快照、网络分区和权限丢失；演练记录链接到 canonical Test ID/追溯 ID，失败即形成阻断行动项。
